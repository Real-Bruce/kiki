# kiki Windows 首版实施计划

本文件保留 P0–P8 范围和验收清单。当前已有 v0.2.1 便携包，实际状态与后续优先级见 [PROGRESS.md](PROGRESS.md)，不重复搭建已有功能。

## A. 执行原则

- 首先阅读 AGENTS.md、PRODUCT_SPEC.md、DESIGN_SPEC.md、PROGRESS.md，并实际查看四张设计 PNG。
- 检查仓库现状，从首个未完成阶段继续。常规实施无需逐文件询问。
- 使用 Rust 原生 Windows 技术栈，保持批准设计。不得以 HTML 页面、模拟截图或静态 UI 假装完成应用。
- 分阶段实现并验证，每阶段更新 PROGRESS.md 并做本地 Git 提交。
- 先解决捕获、混合 DPI、图形资源和中文字输入等高风险问题，避免最后才发现架构不适合。
- 不因某项缺少外部测试条件停止所有独立工作；继续可完成部分，将未验证项如实记录。
- 不保证所有硬件达到拟定性能数字；必须按固定测试环境证明结果，未达标不自动降低要求。

## B. 技术方案

### B1. 工具链与依赖

- Rust 2024 edition，Windows MSVC x64 目标 x86_64-pc-windows-msvc。
- 确认现有 Rust stable、MSVC build tools、Windows SDK；缺少必要环境时报告具体缺项。
- 选择并固定已验证的稳定 Rust 工具链；记录版本；提交 Cargo.lock。
- 首选微软 windows-rs，按需启用 Win32、COM、WinRT、Direct2D、DirectWrite、D3D11、WIC 等功能。
- 不绑定尚未验证的“最新”crate 版本；先验证所需接口，随后固定依赖。
- 其他依赖只为明确需求添加，并记录作用、许可和体积影响。
- 应用以 Rust 实现；标准 Cargo/MSVC 构建所需元数据和少量 PowerShell 脚本不构成增加运行时语言。

### B2. 建议模块边界

初始可以是一个 Cargo 应用包与清晰的模块层级，不为拆分而建立过多 crate。

| 模块职责 | 内容 |
| --- | --- |
| core/geometry | 物理/逻辑坐标、矩形、屏幕区域、边界裁剪和溢出检查 |
| core/session | 截图会话状态、取消语义、对象选择与交互 |
| core/annotation | 形状、文本、笔画、样式、命中检测 |
| core/history | 撤销重做命令；与截图历史库无关 |
| platform/windows | Win32 窗口、消息循环、热键、托盘、屏幕、剪贴板、输入 |
| capture | 捕获后端、帧所有权、错误与取消 |
| render | Direct2D/DirectWrite、主题资源、预览与成图语义 |
| ui | 遮罩、工具条、设置、菜单、贴图 |
| config | 用户配置与版本迁移、原子写入 |
| app | 启动、单实例、资源协调与退出 |

核心模块不引用 HWND、COM、Direct2D 类型。原生绑定与 unsafe 有明确边界。

### B3. 捕获策略

- WGC 是优先验证的正式后端；通过桌面互操作创建显示器捕获对象。
- GDI 可作为普通 SDR 桌面已验证的兼容后端；不得用它静默掩盖 HDR 颜色问题。
- 首版不增加 DXGI Desktop Duplication 这一第三套实现，除非技术验证证明前两者无法满足要求并经用户确认。
- 先验证首帧时间、系统捕获边框/授权行为、混合显示器与资源释放，避免只证明能拿到一张图。
- 捕获 UI 与后端解耦。选择框由本应用实现，不自动把产品流程替换为系统选择器。
- 遵守系统的捕获权限和保护机制，不绕过授权。
- 明确帧池/帧/纹理归属，不在释放帧后继续使用其底层资源。
- 每个会话有唯一代次或取消标记，晚到的回调不能写入已取消会话。
- 截图结束后停止会话并释放临时大缓冲；后台无捕获、无持续刷新。
- HDR 输入正确映射到 SDR 输出，在预览和最终合成中保持一致。

### B4. 绘制与线程

- Win32 消息循环与可见窗口在主线程。
- 捕获、读回、PNG 编码与文件 IO 使用受控工作线程；通知 UI 时不传递悬空资源。
- 使用 Direct2D/DirectWrite 绘制画布和符合设计的组件；必要时用原生文本控件处理 IME。
- 中文输入的候选框定位、换行、焦点和 DPI 必须实测。
- 一套标注语义供预览与输出使用，不依赖再次截取工具窗口来生成成图。
- Per-Monitor V2；界面按逻辑单位绘制，图像与跨屏组合按物理像素计算。
- 每个显示器可以有独立遮罩窗口，共享同一截图会话与全局物理坐标模型。
- 仅在输入、布局、主题、内容改变或必要过渡时重绘。

## C. 分阶段执行

### P0 — 规划基线

已准备：产品规格、视觉规范、执行计划、AGENTS.md 和四张设计稿。

接手时确认这些文件已在 Git 中；如果尚未提交，先检查原因并建立有意义的规划提交。

### P1 — 工程骨架与原生风险验证

工作：

- 检查环境、固定工具链，建立最小 Rust GUI 工程和必要的资源/manifest。
- 使用 MSVC 目标与 PMv2；Release GUI 启动不弹出控制台。
- 建立单实例、消息循环、托盘、热键注册与退出。
- 实现最小真实屏幕捕获链路，测量 WGC 首帧与资源生命周期；必要时验证 SDR GDI 基线。
- 验证 Direct2D 窗口和中文输入控件能协作；确认主要依赖的发布体积。
- 创建平台无关的坐标/会话类型及基本错误结构。

验收：

- 能真实启动、托盘唤起、捕获图像、退出；没有用假图替代。
- 热键冲突可见，重复启动受控。
- 首轮记录大小、启动、后台内存、首帧、捕获边框/权限表现及依赖。
- 对明显无法达到预算的方案先分析并优化；必须变更技术路线时提出具体证据。

建议提交：feat(app): establish native Rust tray and capture foundation

### P2 — 跨屏捕获与坐标基础

工作：

- 枚举显示器、物理范围、缩放、方向与色彩模式。
- 实现每屏冻结图像与跨屏组合，处理负坐标、非相邻屏幕间隙与裁剪。
- 完成捕获失败、取消和显示配置变化的回收路径。
- 建立明确的图像格式、stride、色彩转换及 CPU/GPU 所有权。

验收：

- 有意义的单元测试覆盖坐标变换、负坐标、边界裁剪、混合 DPI 和溢出。
- 实际输出单屏和双屏图片，尺寸与像素对应。
- HDR 与 SDR 结果分开验证；无 HDR 硬件时记录待验证，不标为通过。
- 反复捕获/取消后资源稳定。

建议提交：feat(capture): support multi-monitor physical pixel capture

### P3 — 截图选区与视觉骨架

工作：

- 实现窗口悬停吸附、点击选窗、拖动选区、调整和移动选区、当前屏全屏。
- 实现八个调整点、尺寸标签、快捷键提示。
- 按设计实现 11 控件主工具条和定位策略；已接入工具真实工作，暂未接入控件明确禁用。
- 提前落实浅深主题、图标、圆角、边框、参数条结构和 DPI 适配。

验收：

- 实际运行截图对比 01 和 02，至少检查浅色、深色及高 DPI。
- 从任意方向拖动、边缘极小选区、跨屏拖动与底部工具条回避都可操作。
- 遮罩、工具条不污染导出图片。
- 临时禁用仅允许阶段内存在，最终交付不得保留假按钮。

建议提交：feat(selection): implement Fluent capture overlay and toolbar

### P4 — 可编辑标注与撤销重做

工作：

- 实现矩形、箭头、整条画笔、文字对象。
- 完成选择/命中、拖动、端点/尺寸调整、删除、样式参数。
- 完成中文 IME、多行、重新编辑和文本快捷键优先级。
- 完成操作粒度的撤销重做，合并单次连续拖动，限制历史容量。
- 保证选区调整后的预览与输出裁剪语义一致。

验收：

- 测试命中优先级、对象修改、撤销重做往返、redo 分支清空与裁剪。
- 中文输入实机验证，Enter 不误完成截图。
- 屏幕预览与合成输出中的位置、样式、尺寸一致。
- 一次绘制只产生一项撤销记录，不复制整张底图。

建议提交：feat(annotation): add editable shapes text and undo history

### P5 — 输出与多张贴图

状态：2026-11-06 完成当前单屏 SDR 实施与验收，见 [完成记录](validation/P5_COMPLETION.md)。跨环境遗留仍按原阶段保留。

工作：

- 实现剪贴板图片、原生 PNG 保存对话框、错误恢复。
- 明确复制/保存/贴图互不附带副作用，成功才结束截图。
- 实现多张置顶图片、拖动、滚轮缩放、恢复原比例。
- 实现悬停控件、右键菜单、关闭单张和关闭全部。
- 完成图像共享和资源回收，避免每张贴图继续保留完整桌面快照。

验收：

- 在常见 Windows 应用验证粘贴；PNG 尺寸/内容/透明区正确。
- 保存取消、只读/不可写路径和剪贴板占用后仍可继续编辑。
- 缩放贴图后复制/保存尺寸保持原图尺寸。
- 多张 4K 图像的 CPU/GPU 内存有记录；关闭后资源回落。
- 真实贴图界面对比 04。

建议提交：feat(output): add clipboard PNG export and pinned images

### P6 — 设置、主题与运行体验

工作：

- 按 DESIGN_SPEC.md 与 05-settings-layout.png 完成左侧导航、无外框分组、自动保存状态。
- 完成热键修改/冲突/恢复默认、主题跟随与手动切换、提示配置。
- 完成用户配置加载/原子保存/损坏恢复。
- 开机启动默认关闭，只在用户开启时配置。
- 完成托盘菜单、首次使用提示、版本及第三方许可信息。
- 固定 PNG 等行为显示为静态说明，不做无意义下拉。

验收：

- 每个导航页都真实有用，无后续功能占位。
- 配置重启保持；损坏配置不会导致启动崩溃。
- 改热键失败不会留下无法恢复的状态；托盘入口始终可用。
- 主题切换覆盖工具条、菜单、贴图控件和设置窗口。
- 对照 05 检查布局和信息密度，确认没有把示例壁纸做进应用。

建议提交：feat(settings): finish preferences themes and startup behavior

### P7 — 完整验证、性能优化与视觉修正

工作：

- 完成所有构建、测试、真实 GUI 和输出检查。
- 完成产品规格中的环境矩阵与失败路径；对未具备的环境清楚标注。
- 建立可复用的性能采样方法，记录至少 30 个时延样本及 60 秒 idle CPU。
- 重复截图/取消/贴图/关闭至少 100 次，检查句柄、内存与线程是否持续增长。
- 使用 Release 检查大图副本、线程阻塞、GPU 初始化、纹理释放、持续绘制和二进制依赖。
- 执行最终浅深色、高 DPI、工具条边缘布局和中文文本视觉对比。

验收：

- 不用压工作集、延迟隐藏功能或只测试空白图来伪造性能。
- 所有必要命令通过；失败原因和未验证项记录在报告。
- 对未达标预算有实测证据与剩余差距说明，不能仅写“性能良好”。
- 不继续加功能，集中修复正确性、稳定性和批准设计的一致性。

建议提交：perf(app): validate resource lifecycle and polish approved UI

### P8 — 打包与交付

工作：

- 生成 dist/kiki-v0.1.0-windows-x64.zip，包含 kiki.exe、运行必需文件、简短使用说明和必要许可。
- 不打包源码、设计图、调试符号、开发工具、测试数据或日志。
- 在无开发环境或干净测试环境验证解压运行；检查运行库依赖，满足免安装目标。
- 更新 README 使用说明、PROGRESS、版本变更与最终验证报告。
- 整理源码状态，提交最终改动；生成 ZIP 的 SHA-256。

验收：

- ZIP 可解压启动、截图、标注、输出和贴图；包含功能符合首版范围。
- Git 有完整本地提交历史，工作树无未解释修改。
- 未配置远端时不阻塞本地交付，不自行创建远端或发布。
- 最终答复提供 ZIP 路径、源码分支与提交、实测指标、测试结果及已知限制。
- 只有全部必需验收完成才可以称为首版完成；环境缺失项必须注明。

建议提交：chore(release): prepare Windows v0.1.0 portable package

## D. 验证命令基线

现有工程的验证基线如下，仅记录实际执行结果：

~~~powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --target x86_64-pc-windows-msvc -- -D warnings
cargo test --workspace --target x86_64-pc-windows-msvc
cargo build --workspace --release --target x86_64-pc-windows-msvc
git diff --check
~~~

- 每个阶段运行与改动相关的检查；最终交付运行完整基线。
- 合适的测试：坐标与裁剪、对象编辑和撤销、会话状态转换、取消/失败保留内容、配置恢复。
- GUI、中文输入、图像输出、性能和真实混合 DPI 不能仅凭单元测试判定。
- 可以在阶段中记录 GUI 烟雾检查，不能用录制的设计图代替真实运行结果。

## E. Git 工作流

1. 保留 main 的规划基线，检查当前工作树。
2. 若没有可复用实施分支，创建 feat/windows-v1。
3. 每个阶段以可验证的小批次提交；大阶段可有多个语义提交。
4. 暂存前检查改动，提交前检查暂存 diff、空白错误和敏感/生成文件。
5. PROGRESS.md 与相关说明随阶段提交。不要要求用户逐次确认常规本地提交。
6. 不擅自 squash、amend 既有他人提交或强推；不自动把实施分支合并到 main。
7. 用户未要求远端与发布，仅做本地版本管理及本地 ZIP 交付。
