# v1.0.22 在多图 README 预览中暂停

2026-11-23，用户复测后继续排查。产品代码基线为 `4b96b50`。桌面正在运行的解压版 EXE 资源版本为 1.0.22，SHA-256 与[候选包记录](long-capture-v1.0.22.md)一致，进程启动时间早于附件截图。上轮修复的两类误判有独立回归，本次 180 px 高选区仍能触发暂停。

## 根据附件定位停点

- 排除松绿边框，1920 × 1080 附件中的有效选区为 x=539–1828、y=160–339，即 1290 × 180 px。2220 px 是预览显示的累计长图高度。嵌入图片占选区内 1270 px，两侧有 11 和 9 px 的深色页边。
- 将左侧缩略图内可辨识的设置内容与仓库配图缩放对齐，匹配度最高的是第一张“通用”图。按 2220 px 总高与缩略图比例估算，已收录该图约 610 行。缩略图末端绿框内有连续 27 行像素完全相同。
- 实时选区已出现“设置已保存”及 **Capture** 标题。按 README 顺序，这是第二张“快捷键”图的结尾。附件展示的是先前部分已保留、页面继续向下滚动后的状态。仅凭这张静态截图无法确定第一张被拒的实际帧或采集时序。

## 按附件尺寸重放

取仓库“通用”“快捷键”“截图”三张实图，依次缩放到 1270 px 宽，置于 1290 px 宽的深色底上，每节分配 128 px 显示标题和说明。夹具为 1290 × 3560 px，标题间距与重采样方式为实验设置。用 v1.0.22 的真实拼接器逐帧输入已知位移，按原图检查输出像素。

| 输入与步长 | 实测结果 |
| --- | --- |
| 仅“通用”图，16 px/帧 | 首拒时已收录图顶起 612 行，与附件估算的约 610 行接近。全图为 1045 行 |
| 仅“截图”图，16 px/帧 | 1086 行全部拼入，与源图逐像素相同 |
| 三图，16 px/帧 | 第一处拒绝在文档 y=576，上一次可信位置为 560。两帧重叠 164/180 行，740 行已确认内容与源图一致。随后经过第二、第三张图片仍未恢复 |
| 三图，4 px/帧 | 第一处拒绝仍在 y=576，176/180 行重叠。已确认的 752 行与源图一致 |

三图重放第一次失败时，真实的 +16 px 是搜索范围内唯一的逐字节匹配。164 行重叠中有 162 行完全相同。其余两行与背景分别只有 19、7 个像素不同，单通道差异最大为 3/255。再向下，“通用”图出现连续 529 行完全相同的像素，“快捷键”图有 437 行。哪怕每一帧按时送到，180 px 选区经过其中一段时仍会多次得到一模一样的画面。对齐位置停在此前的可信帧，后续内容离开其重叠范围后也无法直接追加。

## 可利用的位移证据

固定输出仍为 1290 × 180 px，实验扩大用于测量同一正文位移的区域。使用 436 px 高的区域仍中断。使用上方 48 px、选区 180 px、下方 392 px 共 620 px 的区域时，每次 16 px 滚动都能定位。整个滚动过程中原选区扫过的 3120 行与源图对应区间逐像素一致。其余 440 行始终位于原选区之外。该数值取决于本样本内容和布局。

当前 [Windows 捕获实现](../../../src/platform/windows/capture/mod.rs)从显示器取帧，只读回选区矩形。附件中预览位于选区左侧，按[采集遮罩逻辑](../../../src/platform/windows/editor/long_capture.rs)，选区外覆盖冻结画面。扩大这条显示器读回路径会把静止遮罩作为匹配输入。全局排除遮罩还涉及已验证的[远程控制区可见性](long-capture-v1.0.4.md)。

## Windows 上的验证

在独立的 Release 测试程序中，用不抢焦点的 Win32 窗口显示上述文档。在源窗口前放置带有 1290 × 180 px 开口的固定遮罩。使用窗口级 Windows Graphics Capture（WGC）取得 1290 × 620 px 的源画面，在同一帧中取出原选区。另从显示器取帧检查遮罩。每次绘制与采集握手，命中已知输入后才推进，避免把本试验的现象误归因于采样丢帧。

- 连续 185 个位置的窗口帧均与源数据逐字节一致。仅用原选区时保留 692 行，首次拒绝时上下文顶部为 y=528，此时原选区顶部为 y=576。使用上下文测得的位移、验证选区重叠、再从原选区追加，得到正确的 3120 行。显示器帧的 12 个检查点在选区内部看到实时正文，在遮罩覆盖位置读到固定色。
- 首次桌面对照要求边界像素也完全一致，未通过。改为在测试窗口内部核对正文和遮罩后完成对照。双路并行试验 5 次均输出上述相同的像素比对结果，4 次正常退出，1 次在比对完成后以 `0xC0000005` 退出。该异常的具体来源尚未定位。此试验使用受控 GDI 窗口，RustRover 未参与这 185 帧的渲染。
- 随后单独运行两种采集。显示器单路 3 轮，每轮核对 13 个位置的实时选区与固定遮罩。窗口单路 3 轮，每轮 185 帧，输出的 3120 行均逐像素匹配。六轮均正常退出。
- 针对本机最大化的 RustRover 只查询窗口元数据。125% 缩放下，WGC 捕获项报告 1920 × 1020，DWM 可见边界为 (0,0)–(1920,1020)，与客户区一致。GetWindowRect 返回 (−9,−9)–(1929,1029)。若按后者换算，可能双轴各错 9 px。需要通过真实纹理核对选区原点。本次没有向用户的 IDE 发送输入。当前窗口没有读出标准 Win32 纵向滚动条，UI Automation 的两个可见树节点均未暴露 ScrollPattern。

## 独立滚动窗格的反例

在另一组离线试验中，构造两种滚动行为。前 4 步正文与邻区同步，之后一组继续同步，另一组的正文停在 64 px 而邻区继续滚动。两组的 13 帧上下文像素逐帧完全相同。每一步都能从外侧测得唯一的 +16 px，选区的 164 行重叠也完全相同。直接使用该位移会给两组都生成 372 行，而正文已停的那组应为 244 行，虚增 128 行。在另一个样本中，同时要求选区上下两侧都有纹理仍会多出 32 行。

因此下一步应优先验证**能否确定参考内容与选区属于同一滚动容器，并取得该容器的可信位移**。过去几帧同步、同属一个顶层窗口、选区像素吻合，都不能单独作为跨越整屏留白的条件。有可信位移时，在[整帧相同直接返回 Known](../../../src/core/long_image.rs)前处理，并逐帧验证原选区连续覆盖、屏幕与窗口坐标一致、目标没有遮挡。缺少容器证据或中间行缺失时继续保留已有部分。用户报告的 IDE 场景仍是未解决项。

本地试验材料位于 `artifacts/validation/multi-image-investigation/`（夹具生成脚本、重放、独立窗格反例）和 `artifacts/validation/multi-image-window-probe/`（独立诊断源码、Windows 捕获日志）。原始夹具为紧凑 BGRA8，SHA-256 为 `a4e29ffc4d0f8041b9e4e4736a11b1d4a1b0fe002490e7c0a1f564212e072f19`。
