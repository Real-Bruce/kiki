# P2 单屏输出、坐标与取消验证

日期：2026-11-06。状态：进行中。用户明确要求多屏实机验证先跳过，原因是没有验证环境；跨屏功能和原验收目标保持不变。本文不将合成数据测试称为多屏实机通过。

## 本轮改动

- 将显示器枚举拆到平台 display 模块，逐屏记录物理边界、设备名称、系统缩放、旋转方向、刷新率与色彩模式。捕获前后比较两份描述，配置发生变化时放弃本次结果。
- HMONITOR 只留在捕获线程内；交给 UI 的 DisplayInfo 不含原生句柄或 COM 对象，没有添加 unsafe Send。
- 原始 BGRA 图像的尺寸、行步长和 Vec 长度改为私有，只开放固定长度像素切片，避免外部模块破坏复制操作的边界保证。
- 新增独立区域裁剪，保留全局物理坐标，未覆盖区域保持透明；该 API 目前用于开发输出验证，正式编辑器将在后续接入。
- 取消信号实际进入工作线程：分屏捕获前、首帧等待、读回行循环和返回前检查；首帧等待按最多 10 ms 的片段检查信号，取消后仍通过 RAII 关闭 session/pool。10 ms 不是对 D3D 创建、Map 或系统调用阻塞时间的保证。
- UI 在显示变化和退出时发送取消信号；原有 SessionGate 继续拒绝晚到帧。锁屏通知已在补充工作中接入，真实锁屏及显示热插拔仍未完成验收。
- 开发探针新增 --cancel-stress：实际 StartCapture 后置取消信号，检查返回 E_ABORT，连续 100 次后在同一进程和线程恢复正常捕获并写 PNG。
- 只增加 windows-rs 的 Win32_UI_Shell_Common feature，以读取官方逐屏缩放值，没有新增 crate 或应用运行时。

## 补充：锁屏订阅、窗口所有权与失败回退

- 接入当前 Windows 会话的 WTS 通知。锁屏、控制台断开或远程会话断开时，复用同一取消路径：废弃会话代次、置工作线程取消标记、关闭预览。
- 按[微软 WTS 约定](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsregistersessionnotification)，隐藏窗口销毁前注销通知，使用窗口共享状态防止重复注销；没有把“窗口销毁可能自动清理”当作所有权策略。
- 隐藏窗口采用 RAII 管理，WM_NCDESTROY 清空 HWND 并回收 userdata，避免启动中途失败泄漏窗口，或退出后使用被复用的旧句柄。
- 定时器在启动捕获线程前创建并检查返回值；失败时回到空闲状态。线程启动失败时撤销定时器，避免完成消息无法到达导致永远忙碌。这些罕见失败分支尚未通过故障注入实测。
- 新增 windows-rs 的 Win32_System_RemoteDesktop feature，用于 WTS API，不安装或启用远程桌面服务，也不改变系统设置。
- 实际启动最新默认 Release，WTS 注册成功后进入托盘和捕获流程，显示 1920×1080、125% 冻结桌面；观察到诊断输入框中用户输入的“可以正常输入中文，输入法切换正常。this is ok”及后续分行的“1.第一行 / 2.第二行 / 测试没问题。/ this is good！”。原生界面与可访问性文本留存在 artifacts/visual/p2-native-input* 和 p2-native-multiline*。
- 上述输入由用户实际操作，自动化仅读取和留存证据。没有将其当作最终文字标注对象可二次编辑的验收结果。
- 最新默认 Release 为 362,496 字节，真实启动与捕获通过；默认和 all-features 的严格 Clippy 通过，6 项默认测试通过。
- 未主动锁定桌面或更改显示设置。真实锁屏、解锁后恢复、远程断开、热插拔和系统服务尚未就绪等环境仍待验证；上述 100 次取消探针是显式取消路径证据，不替代这些事件的实机结果。

## 补充：原生故障注入与异常退出

本轮将之前仅做代码检查的失败分支，接入真实 Win32 隐藏窗口和消息泵测试。测试钩子只在 cfg(test) 编译，不进入默认或 diagnostics 的运行 EXE。

| 场景 | 实际检查 | 结果 |
| --- | --- | --- |
| 定时器创建失败（注入返回失败） | 不创建工作线程，清空忙碌状态，允许下一次请求 | 通过 |
| 工作线程启动失败（注入 OS 错误） | 撤销真实创建的 Win32 定时器，后续不持续产生 WM_TIMER | 通过 |
| 捕获返回受控错误 | 真实工作线程经通道返回错误，UI 回收线程/接收器/取消标记 | 通过 |
| 工作线程未发送结果即退出 | 真实通道断开后回到可重试状态 | 通过 |
| 活动请求重复唤起 | 不额外创建第二个工作线程，不增加错误报告 | 通过 |
| 显示变化、锁屏、控制台断开、远程断开消息注入 | 向测试窗口发送消息，线程收到取消后故意返回晚到帧；不打开预览、不报告取消为失败 | 通过 |
| 活动工作任务期间清理应用 | 先发送取消、等待工作任务退出、再释放应用状态，测试结束后 APP 为空 | 通过 |
| 隐藏窗口释放 | WM_NCDESTROY 清空共享 HWND，窗口类可成功注销 | 通过 |

测试中的晚到帧是明确的一像素内存夹具，不是截图，也不写出或作为 GUI 实现证据。消息注入没有更改真实显示配置或锁定桌面，不能替代相应环境的实机验收。捕获错误、线程不足和定时器不足同样是受控注入，不是声称本机真的发生资源耗尽。

发现并修复两个问题：

1. 错误弹窗原先在 APP 的 RefCell 可变借用期间显示，弹窗的嵌套消息循环可能再次访问状态。现在先返回错误并结束借用，再报告错误；测试在每次错误报告时尝试重新借用 APP，五次报告均确认借用已释放。
2. 消息循环错误原先可能跳过正常出口的显式清理。改用 AppStateGuard 在正常与异常返回时统一取得状态所有权，取消并等待工作线程，再释放预览，保证发生在 COM Runtime guard 释放前。相关 Drop 测试覆盖仍有活动工作任务的情况。

在加入 AppStateGuard 前还实际运行 30 次独立进程启动与正常 WM_CLOSE 退出回归，全部热键注册成功、退出码为 0，WTS 注册和窗口注销走实际应用路径。数据见 artifacts/performance/startup-lifecycle-regression：

| 指标 | 结果 |
| --- | --- |
| 样本数 | 30 |
| 启动就绪 P50 / P95 / 最大 | 47.658 / 56.117 / 247.161 ms |
| 平均 | 54.300 ms |

沿用 P1 的同机、diagnostics Release、创建时间到托盘与热键注册就绪的方法，未清缓存/工作集、未删除首样本或最大样本，不是最终截图编辑器的端到端时延。

最新默认和 all-features 严格 Clippy 通过，7 项测试均通过，默认 Release 构建为 363,520 字节。最后实际启动默认程序，成功展示真实 1920×1080、125% 冻结画面，界面记录本次 WGC 捕获 84.2 ms；这只是一次正常路径烟雾检查。

复现原生故障测试：`cargo test --workspace native_failure_paths_release_state_and_allow_retry`。当前不存在正式输出操作、文字对象或设置界面的完整失败矩阵，不能据本轮基础设施测试宣称首版完成。
