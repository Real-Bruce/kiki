## 1. 记录方法与环境矩阵

用例结果只可填写“待执行、通过、失败、阻塞、不适用”。执行后附实际日期、构建模式、测试者、版本/commit、EXE SHA-256、命令及证据路径；无证据不得填“通过”。缺少硬件或权限时标“阻塞（环境待验）”，写具体缺少的环境及受影响用例，不视为通过或自动豁免。“不适用”只用于本阶段确实尚未涉及的路径，须给出范围依据，不能用它跳过失败或缺硬件项。历史报告的通过不能直接填写为本版本通过。

代码阶段验证命令基线，执行结果必须另记，以下不是已运行记录：

~~~powershell

~~~

性能按变化执行，不要求每个小修改重跑全部长采样：

- F01/F03：若修改输入、文本布局或绘制路径，测相关响应样本；有资源生命周期改动时执行 COM-AC-012。
- F02：验证高频参数更新和配置写入合并，首次完成该机制后执行 COM-AC-011；后续复用机制且无新风险时无需每阶段重复60秒。
- F04/F05/F08：输出/像素处理路径采至少30个代表性合成或编码样本，记录图像尺寸及峰值；该类耗时无新造达标阈值。资源所有权变更时执行 COM-AC-012；普通启动/截图时延仅在受影响时重测。
- F06/F07/F09/F10：执行关联正确性及GUI检查；仅有新资源路径、失败或性能疑点时增加相应30样本/60秒/100轮测试，并记录触发原因。
- F11：必须执行 COM-AC-010 至 COM-AC-013，启动/首次/后续普通截图分别至少30样本，长截图拼接响应与输出各至少30个有效样本；至少100轮长截图开始/滚动/结束或取消/输出关闭，覆盖成功和失败恢复，完成后测60秒闲置。
- F12：完整功能与打包回归；若仅调整按钮，不机械重跑F11全部长采样。引用F11准确构建和范围，只能称历史基线；本版本新增性能问题或路径变更必须重测。

维持既有启动P95≤500ms、首次截图P95≤500ms、后续截图P95≤200ms及运行文件≤10MiB目标。200%既有时延未达标样本和其他历史缺项继续列入报告；不得删样、混合硬件结果、改变计时口径或自动降低目标。所有性能数据均须说明Release/diagnostics区别、机器、显示器、样本数量和测量起止。

## 4. 失败回归与版本放行

- 每个缺陷记录复现条件、受影响用例、实际结果、证据、修复提交及复测结论。修复后至少重跑失败用例和共享输入/配置/合成路径的相关用例；不覆盖首次失败证据。
- F11切入长截图会立即丢弃所有旧对象、文字草稿及undo/redo，不备份且取消/失败也不恢复，这是已确认行为。输出失败保留的是切入后的当前长图/编辑，不能据共用错误恢复要求恢复旧对象。
- 功能完成以对应全部必需验收通过为准：核心/边界测试、真实深浅GUI、实际输出、相关失败恢复以及受影响实机环境均需证据。新功能的受影响必需环境缺失时保持待验，不能自动认定完成或生成完成标签。与本阶段无关的既有待验项继续在PROGRESS和报告列明，不重复搭建已实现能力，也不把该历史缺项扩为新的豁免。
- 放行顺序：先同步候选版本元数据，再构建候选 EXE/ZIP，执行相关验收及解压烟雾检查，报告绑定被测代码/EXE/ZIP 哈希；修改应用代码或资源后重新构建并复测受影响项。随后同步唯一进度文档及变更记录，检查明确暂存的 diff 和 `git diff --check`，提交并创建本地标签，最后只读核对标签指向和产物。不能先验旧二进制再改版本而省略最终产物验证；报告不得预填未知提交 SHA 或标签已存在。
- 版本采用用户规则：最小修改第三位、小优化第二位、大优化第一位；本轮 F01–F12 计划目标见下表。若额外修补已经占用某计划版本，按规则向上选择未使用且递增的版本并同步计划、进度及报告（如 F06 改为 v0.7.2）；不覆盖或移动旧标签，不把多个未完成功能合并称完成。
- 全部版本只授权本地管理与本地ZIP交付；未明确授权不推送标签、不发布远端Release。若后续需豁免必需验收或改变已批准范围，必须明确报告缺口并取得用户决定，不由代理自行放行。
